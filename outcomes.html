CS 499 · Evidence map

Five course outcomes

Each outcome is linked to work a reviewer can inspect. The individual project demonstrates review and collaboration strategies, not invented professional team experience.

1. Collaborative environments and decision making

The video frames the original problems for review. Instructor feedback led to smart-pointer ownership, sorted/random baseline measurements, and a direct compile fallback. Focused interfaces, comments, verification records, and before-and-after pages help a future maintainer or an advisor assess the decisions. My self-assessment explains team practices and the limits of this individual project.

Feedback incorporated · Readable component boundaries · Reviewer verification path

2. Professional oral, written, and visual communication

The code review video, three readable narratives, Word copies, schema diagram, benchmark table, and navigation adapt the technical detail to different audiences. Each enhancement explains both its technical choice and its user-facing value.

Oral review · Written reflection · Visual performance comparison · Schema and transaction flow

3. Algorithms, computing solutions, and trade-offs

The algorithms stage changes skewed BST behavior to AVL balancing, uses hash-set membership, and checks prerequisite cycles before replacing the catalog. The benchmark includes sorted and random inputs. The narrative explains why additional rotation complexity is worthwhile. The database stage adds graph reachability checks in SQL without claiming AVL benchmark results as database performance.

AVL implementation · Graph validation · Benchmark and trade-offs

4. Tools and techniques that deliver value

Iterative milestones introduce modular C++17, dependency injection, automated tests, SQLite persistence, relational modeling, CRUD, and repeatable builds. The design reduces maintenance coupling; the database saves the advisor's catalog across restarts. All three stages retain CMake and direct compile paths.

Modular design · Persistence and CRUD · Build and test evidence

5. Security mindset and data protection

Explicit validation rejects malformed and inconsistent records. Prepared parameters separate SQL from user values. Foreign keys, deletion rules, cycle checks, and transactions prevent partial or invalid catalog changes. Smart-pointer ownership reduces manual-memory risk. Public samples use synthetic data; the project does not claim authentication, encryption, or production security coverage.

Bound SQL and transaction guard · Storage constraints · Security and integrity tests
