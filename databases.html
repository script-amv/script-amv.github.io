Databases

SQLite turns a temporary catalog into persistent data with clear relationships, bound values, and atomic imports.

Data model and reliability

courses: course_number (PK), title
↑ course_number (FK)   ↑ prerequisite_number (FK)
prerequisites: (course_number, prerequisite_number) (composite PK)

Deleting the owner removes its prerequisite links. Deleting a course still needed by another course is restricted. The target index supports reverse-reference checks. The application inserts all courses before links, checks cycles, and commits only if the full import is valid.

BEGIN → all courses → prerequisite links → cycle check → COMMIT
Any failure → ROLLBACK → previous catalog remains

This helps an advisor keep valid data after an error and return to the saved catalog after restarting. SQLite runs the final catalog; the retained AVL is a separate sample, not a duplicate live cache.

Narrative and reflection

My artifact is the CS 300 Course Planner, a C++ application that I created in CS 300: Data Structures and Algorithms. The original program reads a CSV file, stores courses in memory, prints a sorted catalog, and finds the prerequisites for one course. I selected this artifact because it solves a clear advising problem and can show growth across several parts of computer science. Before this enhancement, all course data disappeared when the program closed. A user also had to edit the CSV file outside the program to make any change. Adding a database gave me a way to improve the same artifact while showing data modeling, SQL, transactions, and secure data access.

The enhanced version uses SQLite as its persistent source of truth. I created a Courses table for course numbers and titles and a Prerequisites table for the relationship between a course and the courses that must come before it. The course number is the primary key in Courses. The two course numbers form a composite primary key in Prerequisites, so the same relationship cannot be stored twice. Both values are foreign keys. If a course owns prerequisite links, those links are removed when the course is deleted. If another course still depends on the course, deletion is restricted. I also added an index on prerequisite_number to support reference checks and deletion rules.

The CSV import is completed inside one transaction. The program removes the old records, inserts all courses, and then inserts prerequisite links. This order allows a prerequisite to appear later in the input file. Primary keys reject duplicate courses, and foreign keys reject missing references. A recursive SQL query checks the prerequisite graph for cycles before the transaction is committed. If any step fails, the transaction rolls back and the previous valid catalog remains in the database. This was an important improvement because the original program could not provide persistent storage or database-level protection against partial changes.

The menu now demonstrates create, read, update, and delete operations. A user can import a CSV file, list courses, find a course, add a course, update its title, or delete it. Every user value is passed to SQLite with a prepared statement and a bound parameter. The program does not join user text into an SQL command. One automated test stores a title containing quotes and SQL-like text and then reads back the same value. This shows that the text is treated as data. Other tests confirm that a prerequisite cannot be deleted while another course still needs it and that records remain after the database is closed and opened again.

This enhancement gives strong evidence toward course outcomes four and five. It supports outcome four by using C++, SQLite, relational design, queries, prepared statements, indexes, and transactions to add useful persistent storage. It supports outcome five through bound values, foreign keys, field constraints, rollback, and safe deletion rules. It also supports outcome two through clear error messages, build instructions, schema documentation, and this narrative. Outcome three remains supported by the AVL tree from the earlier enhancement. Outcome one still needs the clearest final evidence. I plan to show how instructor feedback changed my artifact and portfolio presentation when I complete the final version. The course outcomes ask students to connect technical solutions with communication, professional tools, and security thinking (Southern New Hampshire University [SNHU], n.d.).

The main challenge was preserving a valid catalog when an import failed. I learned that validation in application code is helpful, but the database must also protect its own rules. Inserting every course before the prerequisite links solved the forward-reference problem. The transaction solved the partial-data problem because all steps succeed together or the old catalog is restored. Cycle detection was another challenge because foreign keys can confirm that a course exists, but they cannot alone confirm that the full prerequisite path is valid. I used a recursive common table expression to find a path that returns to its starting course. I also learned that deletion rules should match the meaning of each relationship instead of using the same action for every foreign key.

I added 18 automated test cases covering schema settings, indexes, forward references, missing references, duplicate records, cycles, rollback, prepared values, safe deletion, CRUD operations, file-backed persistence, CSV input, and the earlier AVL behavior. The tests also passed with address and undefined-behavior checks enabled. The application is still a local single-user tool. It does not include accounts, network access, user roles, or encryption key management. Those features would require a larger system design. For this milestone, the database enhancement meets my planned goal by turning temporary CSV data into a tested persistent catalog with clear integrity and security rules.

I completed this database enhancement during Module Five of CS 499. My instructor described it as complete and verifiable and asked me to make the successful direct build path explicit in the README. I added that path, checked both CMake and direct compilation, and kept the schema and test evidence easy to find. I also retained the prepared statements, relationship rules, forward-reference import order, and rollback tests recommended earlier. SQLite is now the application's source of truth: menu reads and updates use SQL, while the AVL implementation remains available for the algorithm comparison. This avoids keeping two live catalogs that could disagree. It is a design trade-off because persistence replaces the in-memory catalog in the final application. Outcome one has further evidence through reviewer-facing instructions and documented decisions, while a real team project remains a future learning goal. Outcome three also has evidence from the recursive cycle query, but the retained AVL benchmark measures the algorithm stage, not database query performance.

Limits and next steps

The simple CSV parser rejects quoted fields and commas inside titles. Updating a course changes its title, not its identifier or prerequisite relationships. Import replaces the whole catalog. Accounts, encryption, access roles, concurrent service behavior, and schema migrations need more design before deployment to a shared organization.
