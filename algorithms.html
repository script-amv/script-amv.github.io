Narrative and reflection

My artifact is the CS 300 Course Planner, a C++ console application I created in CS 300: Data Structures and Algorithms. The program helps academic advisors load a course catalog, print the catalog in course-number order, and look up a course with its prerequisites. I selected the same artifact for this algorithms and data structures enhancement because its original binary search tree had a useful purpose but a clear performance limit. The original program inserted courses in a plain binary search tree. It worked for small input, but it could become a one-sided tree when the file was sorted. This gave me a practical way to show how data structure choices affect a program that users depend on.

I replaced the plain binary search tree with an AVL tree. Each node now stores its height. After every insertion, the program updates heights and checks the balance factor. When a node becomes too heavy on one side, the program performs a left, right, left-right, or right-left rotation. I used unique_ptr ownership for child nodes during the rotations. This was important because rotations move tree nodes while keeping exactly one owner for each node. The enhanced tree still uses in-order traversal, so advisors receive the same sorted catalog. The improvement changes worst-case insertion and lookup from O(n) in the unbalanced tree to O(log n) in the AVL tree.

I also improved prerequisite validation. The original program used a vector and repeated linear searches to check whether each prerequisite existed. The enhanced program uses unordered_set membership for course identifiers and for duplicate prerequisites. This gives average O(1) membership checks. The import process now rejects empty or invalid identifiers, duplicate courses, repeated prerequisites, self-prerequisites, missing references, and multi-course prerequisite cycles. It accepts forward references because all identifiers are collected before prerequisite references are checked. The program builds a staged catalog and replaces the active catalog only after the complete file passes validation. This means a failed import does not leave partial data or remove the user’s previous valid catalog.

I measured the improvement with a benchmark that compares the original-style binary search tree with the AVL tree using 1,000 course keys. With sorted insertion, the baseline tree reached height 1,000 and averaged 500.50 comparisons for a successful lookup. The AVL tree reached height 10 and averaged 8.99 comparisons. With the same keys in a fixed random order, the baseline tree had height 25 and averaged 12.14 comparisons, while the AVL tree had height 12 and averaged 9.30 comparisons. I chose comparisons and tree height instead of only timing because they show the data structure behavior without depending on one computer’s speed. The benchmark source and CSV results are included with the artifact so the measurements can be repeated.

This enhancement gives substantial evidence toward course outcome three because I evaluated an existing design, identified its worst-case behavior, and selected a data structure that has a different trade-off. AVL trees are more complex to implement than plain binary search trees because rotations and node heights must be correct, but they give dependable lookup and insertion performance as the catalog grows. It also supports outcome four through C++ implementation, automated tests, and a reproducible benchmark. It supports outcome five because validation and cycle detection protect the accuracy of prerequisite data. Outcome two is supported through the README, benchmark report, clear error messages, and this narrative. Outcome one still needs stronger evidence from feedback and collaboration, so I will continue to use instructor feedback while polishing the ePortfolio.

The hardest part of this enhancement was making rotations safe with unique_ptr. I learned that a correct AVL rotation needs both correct ordering and safe ownership transfer. Moving the child pointer before reconnecting the parent keeps the tree valid throughout the operation. I added automated tests for sorted output, searches, invalid imports, direct and multi-course cycles, and 2,000 sorted insertions. The sorted-insertion test confirms that the AVL height stays at or below 11 and that a lookup needs no more than 11 comparisons. The next enhancement will add SQLite storage. I will keep the validation rules from this version and add database relationships, transactions, indexes, and prepared statements so that the data stays reliable after the program closes.

I completed this enhancement during Module Four of CS 499, after the software design milestone. For final publication, I applied the instructor's feedback by retaining the baseline BST and AVL measurements, rerunning the tests and benchmark, and adding a tested direct compile fallback beside CMake. The baseline is an original-style, unbalanced BST implemented in the benchmark, not a timing run of the complete original menu program. Sorted and fixed-seed random insertion show both a worst-case order and a less demanding order. The exact random permutation may differ with another standard library's shuffle implementation, so the seed alone does not guarantee identical random counts across all platforms. These checks give a reviewer useful evidence for a design decision. They also support outcome one through an understandable review process, while I still need more experience working in a real development team. In the later database stage, SQLite becomes the active catalog; the AVL remains a separately tested algorithm sample and is not claimed to accelerate SQLite queries.
