Professional self-assessment

Computer science has been my hobby for more than eight years, and I began university about a year ago. The program has helped me turn that interest into a more careful way of working. I want to grow in backend software development, where clear design, reliable data, and testing matter as much as getting a program to run. My strongest improvement is learning to explain a decision and provide evidence that another person can check. I now see a professional work sample as more than code: it should include a clear problem, design choices, limits, and a repeatable way to verify its behavior.

Outside the Course Planner, I helped code the Zsetup website for my father's business. It has not been published yet, so I do not present it as a completed deployment. This gave me a real business context for thinking about who will use a website and how clearly it presents information. My course journals also helped shape my goals. In the marketing journal, I considered how to show useful skills without exposing private data or work that I do not have permission to share. In the career journal, I connected my interests with testing, validation, and professional presentation. In the emerging technology journal, I compared quantum computing and edge computing. These experiences strengthened my habit of matching a tool to a need and explaining its limits.

For collaboration, my clearest experience in this capstone is the review process with my instructor. Saba recommended measuring baseline tree height and lookup counts, deciding on smart-pointer ownership before rotations, and keeping a direct compile command alongside CMake. I used this feedback to make the work easier to review. This is an individual project, not evidence that I led a development team. In a team environment, I would use the same approach: agree on interfaces and acceptance checks, keep changes small, explain trade-offs in code reviews, and let others reproduce the tests. Clear responsibilities and comments about the reason for a change help people with different experience levels take part in a decision. This is how my portfolio supports outcome one without claiming teamwork that it does not show.

Communication is another skill I developed. A technical reviewer needs source files, build commands, tests, and measurements. An advisor or employer also needs to know why the change matters: a failed import should not erase a valid catalog, searches should remain dependable, and saved data should be available after restarting. My video, written narratives, outcome map, and before-and-after pages explain the same work for these different audiences. The journals gave me practice connecting technical choices with career goals and public-sharing risks. Together, these provide evidence for outcome two through oral, written, and visual communication.

My work with data structures taught me to consider both the normal case and the worst case. A plain binary search tree is simpler than an AVL tree, but sorted input can make it behave like a linked list. I learned to weigh implementation complexity against more dependable search and insertion. With 1,000 sorted keys, the baseline height was 1,000 and average successful lookup took 500.50 comparisons. The AVL height was 10 and lookup took 8.99 comparisons. I also used hash sets for average constant-time prerequisite membership and graph traversal to reject cycles. These measured choices support outcome three. They are structural measurements, not a claim about database speed or all real workloads.

In software engineering and databases, I learned to separate responsibilities before adding more features. Input parsing, business validation, storage, and the menu have different jobs. A replaceable repository boundary and stream-based menu make testing easier. SQLite then adds persistent records, relational keys, deliberate indexes, and transactions. I tested the enhancement stages separately before treating them as one project. The design stage has 15 passing checks, the algorithm stage has 16, and the database stage has 18. These are separate suites, not 49 unique behaviors. CMake instructions and tested direct compile fallbacks make the work easier for another developer to run. This supports outcome four through tools that solve a clear advising problem.

Security means planning for bad input and failures, not only reacting after something breaks. I used explicit validation, safe ownership, prepared SQL values, foreign keys, and transaction rollback. Tests check missing references, duplicates, cycles, SQL-like titles, and failed imports that preserve the old catalog. This supports outcome five and helps protect data accuracy. The project uses synthetic course data and is a local, single-user tool. It does not provide accounts, encryption, shared-user permissions, or a full production security review. I would need to design those controls before using it as a shared university service.

The portfolio presents one artifact in three stages so the growth is easy to follow. The original CS 300 Course Planner shows the starting point. The software design version separates responsibilities and improves validation. The algorithms version adds balancing, prerequisite checks, and benchmark evidence. The database version adds reliable persistent storage and CRUD operations. SQLite is the final application's source of truth; the AVL implementation remains separately available and tested, rather than being described as the database's query engine. The code review introduces the issues, and each narrative explains the learning behind the change. Together, these pieces show my progress toward all five outcomes and the careful, evidence-based developer I want to become. My next goals are to gain more real team experience and continue improving backend design, testing, and secure data handling.
