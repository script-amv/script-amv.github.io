Enhancement One · Module Three

Software design and engineering

From a single source file to focused C++ components, with safer ownership and imports that preserve the previous valid catalog.

What changed

The original combines storage, validation, file access, and the menu. This stage gives each responsibility a clear boundary. The repository interface supports replacement and test doubles; stream-based menu input makes interaction testable. A staged import validates the whole catalog before replacing it.

Menu → CourseService → CsvCourseRepository
CourseService → validate staged data → CourseTree

For the advisor, an import error no longer means losing the last valid catalog. For a maintainer, code changes are easier to isolate and test.

Narrative and reflection

My artifact is the CS 300 Course Planner, a C++ console program that I created during CS 300 before this capstone course. It helps academic advisors load a course catalog, print courses in order, and look up a course and its prerequisites. I completed this software design and engineering enhancement during Module Three of CS 499. I selected this project because it already solves a clear problem, but its original design gives me room to show how I can improve a working application. Computer science has been my hobby for more than eight years. This project helps me connect that interest with the more careful design practices I have been learning at university.

The original program puts the tree, file loading, validation, and menu in one source file. In the enhanced version, Course holds the data, CsvCourseRepository reads the file, CourseService checks the records, CourseTree stores the catalog, and Menu handles input and output. CourseRepository provides an interface so a different source can be added later. These changes show separation of responsibilities, dependency injection, and reusable C++ design. The menu can now be tested with input and output streams instead of a person entering every command. I also replaced manual node ownership with unique_ptr and created the application objects on the stack. This makes ownership clearer and avoids manual delete calls in the application.

One improvement that matters to an advisor is reliable file loading. The original program could load part of a file and still report success. It could also add duplicate records when the same file was loaded again. The enhanced service builds a temporary catalog, checks every record and prerequisite, and replaces the active catalog only after the whole import succeeds. If a file fails, the previous catalog remains available. The program rejects empty titles, invalid or duplicate course numbers, missing or repeated prerequisites, and self-prerequisites. It accepts lowercase course numbers and forward references. The menu supports file paths with spaces and exits cleanly when input ends. The parser clearly rejects quoted CSV, because support for that format would need additional parsing rules.

My Module One plan connected this enhancement to outcomes one, two, four, and five. This version provides concrete evidence toward outcomes two, four, and five through readable messages and documentation, modular design, safer ownership, validation, and automated tests. The course describes these outcomes in terms of professional communication, useful computing solutions, and a security mindset (Southern New Hampshire University [SNHU], n.d.). I have made progress, but I am not claiming full achievement of every part. Documentation and clear interfaces can help future collaboration, but they do not prove that I have worked with a team or used stakeholder feedback. Outcome one still needs that evidence. Outcome three has some support from explaining design trade-offs, while the main algorithm enhancement remains planned for the next milestone.

The main lesson from this enhancement is that a program can work on normal input and still need better boundaries and error handling. The hardest design issue was deciding when new data should replace old data. Checking records one by one was not enough because a prerequisite might appear later in the file. Building a temporary tree and checking references after all courses were added made that rule easier to follow. Another challenge was memory cleanup. Smart pointers express ownership, but a long tree can still cause deep recursive destruction. The enhanced tree uses an iterative cleanup procedure, and the tests include a skewed tree with 2,000 records. This helped me see that safer tools still need careful use.

The automated tests cover valid loading, sorted output, normalized searches, forward references, rejected imports, preserved data after errors, repeated loading, menu input, and CSV errors. I used these checks to make the behavior repeatable instead of relying only on a successful demonstration. The tree is still unbalanced, so worst-case search and insertion can take linear time. Multi-course prerequisite cycle detection is also still a limitation. SQLite storage and AVL balancing remain later enhancements. My next steps are to review instructor feedback, improve the artifact where needed, and connect the final code and narrative to my ePortfolio. This work moves the project toward a professional sample by making its behavior easier to explain, test, and maintain.

For the final portfolio, I incorporated the instructor's feedback by keeping the build and test evidence and adding a direct C++17 compile path beside CMake. Both paths were checked again. This stage preserves the before-and-after design work; AVL balancing and SQLite are shown in their own later stages. The change supports an advisor by keeping the last valid catalog after an import fails, and supports another developer by making responsibilities and verification steps clear. Outcome one now has evidence from my response to the code review and feedback process, although this individual project does not prove experience leading a team. The final portfolio connects this work to the later stages instead of presenting the planned enhancements as unfinished features of this version.

Build without CMake

From the extracted design ZIP folder:

mkdir -p build-direct
c++ -std=c++17 -Wall -Wextra -Wpedantic -Ienhanced/include enhanced/src/Repository.cpp enhanced/src/Tree.cpp enhanced/src/Service.cpp enhanced/src/Menu.cpp enhanced/src/main.cpp -o build-direct/course_planner
c++ -std=c++17 -Wall -Wextra -Wpedantic -Ienhanced/include enhanced/src/Repository.cpp enhanced/src/Tree.cpp enhanced/src/Service.cpp enhanced/src/Menu.cpp enhanced/tests/tests.cpp -o build-direct/planner_tests
./build-direct/planner_tests
./build-direct/course_planner

The ZIP's README also includes CMake commands. The tree is intentionally still unbalanced in this stage, and multi-course cycle detection arrives in the algorithms enhancement.
