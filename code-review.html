CS 300 Course Planner Code Review

This review examines the original C++ Course Planner before its capstone enhancements. The application helps academic advisors load a course catalog, print courses in order, and find course prerequisites.

Existing functionality

The original project reads course data from a CSV file. It stores a course number, title, and prerequisite list for each course. A menu allows a user to load the data, print the catalog in course-number order, or search for one course and display its prerequisites.

Review findings

The original project uses one source file, raw pointers, a plain binary search tree, and repeated vector searches for prerequisite validation. The tree can become one-sided when courses are inserted in sorted order. That creates O(n) worst-case insertion and lookup behavior. The CSV-only design also means the catalog is temporary and cannot support controlled updates after the program exits.

Enhancement plan

Software design and engineering

Separate file access, validation, catalog storage, and menu behavior into focused C++ classes. Use safer ownership, clearer errors, and automated tests.

Algorithms and data structures

Replace the unbalanced tree with an AVL tree and use hash-set membership for course and prerequisite checks. Compare tree height and lookup counts for sorted and random input.

Databases

Add SQLite storage for courses and prerequisite relationships. Use constraints, transactions, indexes, and prepared statements to protect data quality.

Feedback incorporated in the final work

The instructor recommended baseline height and lookup counts for sorted and random input, clear ownership before rotations, and direct build instructions alongside CMake. The published algorithms stage includes the original-style BST comparison and unique_ptr rotations. The database stage includes prepared values, forward-reference imports, deliberate keys and indexes, and rollback tests. Every stage has a reproducible verification record.

The original review video remains the starting-point record. This follow-up explains how the feedback was applied rather than suggesting that the original recording includes later test results.
